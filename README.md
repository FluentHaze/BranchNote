# BranchNote

按项目管理功能分支，单条或批量提交测试、发布 MR。React + TypeScript + Vite + Electron，数据保存在本地。

## 运行

需要 Node.js 22.16 或更高版本和本机 Git。

```sh
npm install
npm start
```

浏览器预览：`npm run dev`。浏览器无法访问本地 Git，提交 MR 请使用桌面应用。

## 使用

1. 新建项目，通过“从仓库添加分支”关联仓库，挑选功能分支。
2. 在“MR 目标”中选择已存在的远程测试、发布分支。
3. 点单行的“提交测试 / 提交发布”，或勾选多个功能分支批量提交。
4. 提交面板显示所选分支、阶段和目标，确认后点“提交 MR”。批量选择会汇总为**一条 MR**。
5. 应用从目标分支创建独立的 `mr/*` 源分支，把功能分支汇总到它上面，再推送源分支并创建 MR。功能分支和目标分支不会因此被改写。
6. 如果遇到冲突，创建 `resolve/*` 临时分支，在应用里选择我方、对方、两边都要，或编辑内容。解决后自动继续汇总，最后提交 MR。冲突会话保存了目标信息，重启后可恢复。
7. MR 创建成功后，列表显示“MR 待合并”并提供打开链接。当前项目按设置的周期（30 秒、1 分钟、2 分钟、5 分钟、10 分钟、15 分钟，默认 30 秒）自动同步平台状态，进入项目、返回窗口也会刷新，支持“刷新 MR”手动同步。关闭显示“MR 已关闭”，合并自动记录平台合并时间；重新打开恢复待合并。应用不会合并 MR，也不会自动部署。
8. 推送失败时停止创建 MR；可在结果面板重试。缺少令牌时可配置令牌，或打开预填创建页手动创建，再重试关联记录。
9. 分支有新修改时点击“已合并”重置为待提交。重置测试会同时重置发布状态与 MR 记录。
10. 删除记录只删除本地台账，保留仓库真实分支。归档项目保留历史。

目标必须是已有远程分支。工作区必须干净，Git 身份、认证和钩子沿用仓库配置。分支更新需要主动执行 fetch；提交使用当前远程跟踪引用，请提交前按需更新。

## 代码托管令牌

在“数据与设置”按域名配置 GitLab / GitHub 令牌，自建平台应明确选择平台类型。GitLab 需要 API 写权限，GitHub 需要仓库访问及 Pull requests 写权限。令牌通过 Electron safeStorage 加密，不进入台账与 JSON 备份。系统钥匙串不可用时界面会提示。

## 本地数据与备份

通过“数据与设置”导出、恢复 JSON。恢复前自动备份；浏览器与桌面数据相互独立。

Windows 数据一般位于 `%APPDATA%/branchnote/branchnote.json`；macOS 位于 `~/Library/Application Support/branchnote/branchnote.json`，以 Electron userData 为准。令牌单独存储在 hosts.json，换设备后重新配置。

旧版合并记录保留为历史状态。旧版未完成的直接合并会话需要先放弃，再重新提交 MR。

## 验证与打包

```sh
npm test
npm run build
npm run test:mr-ui
npm run pack:win
```

MR UI 测试使用隔离数据及模拟平台接口，不操作真实仓库、令牌或远程。覆盖批量 MR、推送失败中止、重试、待合并记录和单条发布；Git 测试使用临时仓库检查真实合并与冲突恢复。

Logo 源文件为 public/logo.svg，桌面图标为 public/icon.png 和 public/icon.ico。

macOS 上用 `npm run pack:mac`。安装包输出到 release。当前未配置签名、公证或自动更新，macOS 打包及安装需在对应平台验证。

## 界面与字体

当前采用 A 轻量清单桌面布局：功能说明在上、分支名在下，勾选后统一提交。单条提交也可通过每行“更多”菜单打开。

界面字体 Noto Sans SC、分支等宽字体 JetBrains Mono 均位于 public/fonts，随应用本地打包，不依赖字体 CDN。来源与许可证见 public/fonts/README.md。完整中文字体约 17 MB，保留任意项目名称和备注的字形覆盖。

提交弹窗可展开“账号与令牌”配置 GitLab / GitHub 访问令牌，也可从侧栏“设置与令牌”进入。Git 推送使用本机已有认证；平台 MR 接口使用保存的令牌。测试和发布目标的远程分支下拉框支持搜索、回车选择。列表点击功能说明可编辑“改动备注”，备注直接展示在分支行。

## 提交前冲突检查

提交面板可单独点击“检查冲突”，提交 MR 时也会自动先检查。检查在临时独立仓库内按功能分支顺序试合并，不切换当前仓库、不修改功能分支和目标分支，也不会推送或创建 MR。

发现冲突时显示发生冲突的分支与文件，直到你点“确认，创建 resolve 分支继续”才创建 resolve/** 分支。在该分支解决冲突、合并剩余功能，完成后推送它并作为 MR 源分支。未处理的后续分支可能还有冲突，会逐轮解决。取消确认不会改动仓库；实际合并后放弃会返回原分支并清理 resolve 分支。

检查使用当前已获取的远程跟踪引用，提交前请按需更新远程分支。功能与目标引用若在检查后发生变化，实际执行会拒绝旧清单，需要重新检查。resolve 源分支在 MR 创建后保留，以供平台合并使用。

## 多目标与当前提交流程

项目页点“MR 目标”旁的加号，可添加、改名、删除目标并选择区分色。各目标的 MR 与合并状态独立记录；旧版测试和发布记录继续保留。

单个功能分支无冲突时直接作为 MR 源分支，不生成 mr/* 分支。多个功能先整合为一个分支，然后合入目标分支检查；如有冲突，先由用户确认，再使用指定的冲突处理分支解决并提交。冲突分支输入默认 resolve（自动生成 resolve/时间戳），也支持完整的新分支名。

MR 标题默认读取最后一个所选功能分支当前提交的说明，没有说明时用分支名；可编辑。描述默认留空。

列表在 MR 创建成功后立即显示 MR 待合并，使用本机保存的令牌同步 GitLab / GitHub 状态。应用在前台时按「设置与令牌 → MR 状态同步」选择的周期检查当前项目，返回窗口立即检查；后台暂停轮询。批量提交共享同一 MR 时只查询一次。已合并的 MR 停止轮询；已关闭的继续检查，以支持重新打开。令牌失效、权限不足或网络错误会显示提示并保留原状态。

状态接口：[GitLab](https://docs.gitlab.com/api/merge_requests/)、[GitHub](https://docs.github.com/en/rest/pulls/pulls)。

桌面仅右侧内容区滚动。添加分支固定归属当前项目；项目编辑显示仓库概要。项目删除会确认并只删除应用内台账，不操作仓库文件、Git 分支或平台 MR。点击列表整行可勾选，复制、状态和菜单等控件保留独立操作。
