# BranchNote 推荐 Git 工作流

日常在功能分支开发；提交测试或发布时，通过 MR 把功能送到目标分支。有冲突时，在专门的整合分支解决，再用它提交 MR。合并与审核仍在 GitLab / GitHub 完成。

以下以 `feature/login`、`feature/cart` 为功能分支，`origin/test` 为测试目标、`origin/release` 为发布目标。分支名仅作示例，目标应选团队实际使用且已经存在的远程分支。

## 1. 各类分支分别做什么

| 分支 | 用途 | 是否继续写日常功能 |
| --- | --- | --- |
| `feature/login` 等 | 保存单个功能的开发提交 | 是，在对应功能分支开发 |
| `test`、`release` 等目标 | 接收审核后的结果 | 遵循团队规则，通过 MR 接收本次变更 |
| `mr/阶段-时间戳` | 汇总本次选择的多个功能，并纳入目标分支以检查兼容性 | 不用于日常开发 |
| `resolve/时间戳` 或指定名称 | 解决本次整合中的冲突，保存最终可提交的结果 | 只处理本次整合与冲突 |

`mr/*` 和 `resolve/*` 都属于一次提交的工作分支。“临时”描述其用途：一旦作为 MR 源分支推送，就必须保留到 MR 完成，不能解决完冲突就删除。

## 2. 提交前准备

1. 在原功能分支完成代码修改和必要验证，提交到 Git。
2. 检查没有未提交或未跟踪文件，也没有尚未完成的 merge、rebase 或 cherry-pick。可以先自行提交，或保存尚不准备提交的工作。
3. 更新远程分支引用，再在 BranchNote 选择功能分支和本次目标。
4. 核对这次确实需要一起提交的功能。多个勾选项会成为同一条 MR，不能在平台单独审批其中某一个功能。

提交测试和提交发布是两次独立操作。发布时重新选择本次要发布的功能并以发布分支为目标，不要因为测试已合并，就直接把整个测试分支作为发布内容；团队明确采用整条测试分支晋级的流程时另行遵循团队约定。

## 3. 没有冲突时如何走

**只选一个功能**：预检通过后，直接推送该功能分支，以它为源向目标创建 MR，不额外创建 `mr/*` 分支。原功能分支的提交历史不会被整合操作改写，但它会作为 MR 源分支被推送。

**选多个功能**：应用从第一个所选功能分支的当前提交创建 `mr/阶段-时间戳`，依次合入其余功能分支，最后合入目标分支，再推送该整合分支并创建一条 MR。

合入方向是“目标内容进入整合分支，用于检查兼容性”，不是应用把内容直接写入目标。平台审核并合并 MR 后，目标分支才更新。

## 4. 发现冲突后，先理解两个阶段

**预检阶段**：应用在隔离的临时仓库中，从第一个所选功能分支开始，依次合入其余功能分支和目标。发现冲突会列出文件并等待确认。此时你的原仓库没有切换分支；取消不会创建冲突处理分支，也不会推送。

**确认处理阶段**：点击“确认，创建 resolve 分支继续”后，应用才在你关联的真实仓库中创建并切换到指定的冲突处理分支。默认输入 `resolve` 会生成 `resolve/时间戳`，也可填写新的完整名称。

这条分支从**第一个所选功能分支**的提交出发，不是从目标分支出发。它会按顺序吸收其余功能分支，最后吸收目标分支。任何一步冲突都在这条分支上解决，原来的功能分支和目标分支不因此被改写。

例如本次选择登录和购物车，目标是测试：

```text
feature/login 的提交
  → 创建 resolve/本次提交
  → 合入 feature/cart，若有冲突则解决并提交
  → 合入 origin/test，若有冲突则再次解决并提交
  → 推送 resolve/本次提交
  → 创建 MR：resolve/本次提交 → test
  → 平台审核、合并后，test 才更新
```

只选一个功能但它与目标冲突时，同样从该功能创建 `resolve/*`，在其中合入目标并解决，然后以 `resolve/*` 提交 MR。

## 5. 用户在冲突面板里怎么操作

1. 确认当前提示的处理分支名称。后续修改都应留在该分支，不要在处理过程中手动切回功能分支或目标分支。
2. 逐个检查冲突文件。可以选择“采用我方”“采用对方”“两边都要”，也可手动编辑最终内容。
3. “我方”是**当前整合分支已有的内容**，“对方”是**这一轮正在合入的分支**。合入购物车时对方是购物车；最后合入测试目标时对方变成测试分支，不能一直把“我方”理解为目标分支。
4. 手动编辑后点击“保存并标记已解决”。使用外部编辑器时，保存只是同步内容，仍需回应用确认并标记解决。
5. 快捷采用操作会标记文件已解决；本轮所有文件处理完后，应用会提交解决结果并继续剩余分支。后续再次冲突就重复处理，直到全部完成。
6. “两边都要”只是保留双方文本，不保证业务逻辑正确。提交前审阅组合结果，并完成团队要求的测试。

应用处理 Git 冲突并不代表它已经替你验证代码语义。若需要提交前额外测试，先用独立的“检查冲突”了解风险；进入真实处理后，全部解决可能自动进入推送和建 MR，不要假定存在固定的“测试后再发布”暂停步骤。已创建的 MR 可先保持未合并，由团队检查通过后再合并。

## 6. 解决之后，用哪条分支提交

预检已发现冲突并由用户确认的标准路径，会把 `resolve/*` 本身作为最终 MR 源分支。解决提交保留在它上面，应用推送它并创建 MR，不要求用户手动把结果合回原功能分支。

在平台核对：源应为本次 `resolve/*`，目标应为选定的 `test` 或 `release`。不要把 MR 方向反过来，也不要在本地直接合并到目标后绕过审核。

推送失败时先修复认证、网络或权限，再从结果面板重试；失败时不会继续创建 MR。推送成功但平台建 MR 失败时，可配置令牌后重试，或打开预填创建页手动创建，再回应用重试关联。

## 7. 暂停、放弃与清理

- **暂时离开**：未完成的冲突会话会保存，重开应用后可继续。期间不要自行切分支或启动另一次合并，以免会话与实际仓库状态不一致。
- **决定放弃**：使用应用的“放弃本次合并”，应用尝试中止合并、返回原分支并清理对应处理分支。此路径没有提交 MR；若有 Git 错误，先查看当前仓库状态，不要再重复发起操作。
- **MR 已创建但未完成**：保留远程源分支和解决结果；不要因其名称是 `resolve/*` 就删除。继续检查 MR 内容和平台 CI。
- **MR 已合并**：刷新应用确认已合并，再按团队规则删除不再需要的远程整合分支，并清理本地分支。应用不会把本次 MR 源分支自动全部清理掉。
- **MR 已关闭**：先决定重新打开还是放弃这次内容，再清理，避免丢掉尚未合入的解决结果。删除应用内台账不会删除任何真实分支或 MR。

## 8. 后续开发与再次发布

日常功能继续在原功能分支开发，不把 `resolve/*` 当成长期功能分支。需要保留的修复逻辑，应由开发者按团队约定同步到后续开发分支；本次冲突解决不会自动回写到原功能分支。

测试通过后提交发布，应重新针对发布目标预检并整合。测试阶段生成的 `resolve/*` 可能含有仅属于测试目标的代码，不应直接拿它向发布目标提交，除非团队已经审阅并明确决定晋级这一整份内容。

原功能有新提交时，在台账中重置对应目标状态，再发起新的提交。状态代表记录的那次 MR，不是对未来每次提交的自动保证。
