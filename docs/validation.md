## 2026-11-06 修复：编辑器轮询抢先把中间保存提交进合并

起因：真实使用中合并 `feature/api-refactor` 时，用户在 VS Code 里清掉冲突标记后还在继续改，轮询把一个无标记的中间保存（约 2.4 秒未变化）当成了最终结果，自动提交合并、删除 resolve 分支并推送；用户随后保存的真正最终版本只能留在工作区被暂存，没进合并提交。

1. **轮询只同步、不提交**：`ConflictResolver` 的编辑器回读改为——检测到稳定且无冲突标记的保存时，把内容同步进应用内编辑区并提示确认（「确认无误后点保存并标记已解决」），不再自动 `git add` + 提交。解决与否永远由用户的点击决定，中间保存最多同步进编辑区（会被后续保存覆盖）。
2. **提交以工作区最后一次保存为准**：`commitResolution` 在提交前执行 `git add -u`，标记已解决之后又在外部编辑器里继续改的内容也会被收进合并提交（合并开始前强制工作区干净，`-u` 不会卷入无关改动）。
3. 现场修复：把被暂存的最终解决内容 amend 进合提交（保留双亲）并强推 origin/test。

验证：`npm run test:stage` 用例 4 重写并加回归断言——写入无标记内容后出现「已同步编辑器保存的」、编辑区内容已同步、再等 4 秒必须仍在冲突页（不自动提交）、点「保存并标记已解决」后走完合并与推送；`npm test` 35/35；`tsc --noEmit`、Vite 构建与 `node --check electron/git.cjs` 通过。

## 2026-11-06 修正：阶段由用户决定 + 冲突可直接在编辑器解决

起因：一键提交把「合到哪条分支」也一并自动化了，实际使用时变成默认走 release；冲突只能在应用内的小编辑器里改，不如 VS Code 顺手。

2. **冲突可直接用编辑器解决**：新增 IPC `repository:conflict-open`（`shell.openPath` 交给系统默认编辑器）与 `repository:conflict-read-file`（回读工作区文件）。`ConflictResolver` 增加「用编辑器解决」按钮，点击后每 1.2 秒回读该文件；连续两次读到相同且不含 `<<<<<<<`/`=======`/`>>>>>>>` 的内容，就自动 `git add` 标记已解决并继续下一个文件/分支。切换文件时停止轮询，避免误判下一个文件。
