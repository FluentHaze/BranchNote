- `src/login.js` 出现在工作区

**校验**（可选，在 TestBranchNote 目录执行）

## 场景 6：用编辑器解决冲突（重点）

1. 提交 `feature/discount`，进入冲突页
2. 点工具栏第一个按钮「用编辑器解决」

**预期**
- 系统默认编辑器（VS Code / Cursor）打开 `src/config.js`
- 应用里提示「已在编辑器打开 …，改完保存会自动同步到下方编辑区」
- 你在编辑器里把冲突标记删掉、改成最终内容，**保存**
- 应用检测到保存（约 2~3 秒）后把内容同步进编辑区，并提示你确认——**不会自动提交**（防止把编辑到一半的中间保存当成最终结果）
- 你回应用看一眼内容，点「保存并标记已解决」；全部解决后自动继续
- 标记解决之后又在编辑器里继续改了也没关系：提交以工作区最后一次保存为准
- 如果文件里还留着 `<<<<<<<` 等标记，应用不会动它（不会误判）

## 场景 12：受保护的发布分支（MR 流程，重点）

1. 点开「本版本目标」栏 → 给**发布分支**勾上「这条发布分支受保护（只能通过 MR 合入）」→ 保存
2. 目标栏的发布分支色块上应出现**锁标**
3. 在 `feature/login` 行点「提交发布」

**预期**
- **不直接合并、不推送 `origin/release`**：本地与远程的 `release` 都保持 `08bba0e` 不动
- 从 `origin/release` 拉出集成分支 `mr/release-<时间戳>`，`src/login.js` 合入集成分支
- 集成分支推送到远程（`git branch -r` 能看到 `origin/mr/...`）
- 完成页说明目标分支未直接推送
- **功能分支全程干净**：`git rev-parse feature/login` 前后不变
- 配了令牌且远程是 GitLab / GitHub 时：完成页标题「已创建合并请求（MR）」并显示编号，浏览器自动打开 MR 页面
- 本地远程是裸仓库（不是 GitLab / GitHub）时：标题为「已推送集成分支，等待创建 MR」，并说明“无法自动创建 MR”的原因
- 没配令牌时：标题同上，点「去设置令牌」可直接跳到设置页；「打开 MR 创建页」仍可用
- 冲突场景同理：冲突在集成分支的临时分支上解决，功能分支不会被修改

```bash
git rev-parse release origin/release feature/login   # 三个都不变（MR 前后）
git branch --list 'mr/*'                             # 集成分支存在且已推送
```

测完把「受保护」勾掉，或保持勾选体验 MR 流程。

## 场景 15：代码托管令牌（一键建 MR / PR）

1. 侧边栏点「数据与设置」→「代码托管令牌」
2. 填平台地址（如 `gitlab.company.com`，也可粘贴完整 `https://…`）、选平台类型、粘贴访问令牌 →「保存令牌」

**预期**
- 保存后出现一行：`GitLab` 标签 + 域名 + `••••••<末四位>`，界面任何位置都看不到令牌原文
- 令牌写入应用数据目录的 `hosts.json`，字段为 `encrypted: true` 的密文（系统钥匙串可用时）

## 需要重点观察的体验点

1. 点「提交测试」或「提交发布」后**是否真的只点一次**就能跑完（无冲突场景）
2. 冲突时点「两边都要」后**是否自动接力**到下一个文件/分支
3. 自动推送过程中提示是否为「正在推送…」（不应显示「远程还是推送前的提交」）
4. 放弃合并后是否**不会**卡在 `resolve/*` 分支
5. 完成页信息是否说清：合到哪个分支、合了哪些、推没推成功
