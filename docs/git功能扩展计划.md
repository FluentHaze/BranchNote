# BranchNote Git 功能扩展计划

更新日期：2026-11-10

状态：规划待实施；本文不是功能已上线或验收通过的说明。

## 1. 目标与使用路径

在现有分支台账和 MR 工作流基础上，逐步补齐日常 Git 操作，让用户能够在 BranchNote 中完成：

选择仓库 → 创建或切换分支 → 查看改动 → 暂存 → 提交 → 获取远程更新与推送 → 创建 MR → 跟进平台状态。

首期聚焦这条路径。提交历史和 Stash 放在后续阶段；Revert、Cherry-pick、Rebase、Reset 和强制推送分阶段实施，不要求一次建设完整 Git 客户端。

本文为后续实现的任务依据。每次只实施用户指定阶段，完成后更新该阶段状态、验证结果及剩余限制，不自动推进到下一阶段。

## 2. 当前基础与能力边界

以下基于当前源码梳理，不代表真实仓库和双平台均已验收。

| 当前能力 | 可复用基础 | 扩展时需要注意 |
| --- | --- | --- |
| 仓库及分支读取 | `electron/git.cjs` 的 `readRepository` | 尚不是完整工作区状态、文件 diff 或历史视图 |
| 获取远程引用 | `fetchRepository`，逐个远程 fetch 并清理失效引用 | Fetch 不等于将远程提交合入当前分支，不能把它显示为 Pull 已完成 |
| 推送源分支 | `pushBranch` | 目前服务于 MR 流程，需要补充通用推送入口和上游状态展示 |
| MR 冲突预检与整合 | `prepareMerge`、`checkMerge`、`executeMerge` | 保持现有单分支及多分支 MR 行为，不混入日常 Pull 的会话 |
| 冲突文件处理 | `readMergeState`、冲突读取、编辑、提交及放弃方法 | 当前围绕 MR 合并会话，不能直接假设可用于 Rebase 或 Cherry-pick |
| 平台 MR / PR | `electron/hosts.cjs`、`SubmitDialog`、MR 状态同步 | Git 远程认证与平台令牌继续分开管理 |
| 主进程与界面通信 | `electron/main.cjs`、`electron/preload.cjs`、`src/storage.ts` | 新功能沿用明确的 IPC 方法和 TypeScript 类型 |
| 数据与界面 | React、现有项目页面、弹窗、选择器和本地台账 | Git 状态从仓库读取，不把台账当作 Git 状态来源 |

## 3. 界面组织方向

保留现有“功能分支与 MR”页面。在项目内增加“工作区”和“提交历史”入口，具体导航样式在对应阶段结合现有布局实现。

| 区域 | 负责内容 |
| --- | --- |
| 功能分支与 MR | 现有台账、多目标、提交 MR、冲突预检和平台状态 |
| 工作区 | 当前分支、改动文件、暂存区、diff、提交和同步入口 |
| 提交历史 | 提交列表、详情和后续提交操作 |
| 分支选择器 | 展示当前真实分支，支持创建、切换与远程分支跟踪 |
| Stash 面板 | 保存记录、查看、恢复与删除 |

真实 Git 操作与台账操作必须使用不同文案。例如“删除台账记录”不能简称为“删除分支”；创建本地 Git 分支后也不自动把所有分支加入台账，由用户选择是否跟进。

### P0：仓库状态与操作协调

范围：

- 增加统一的仓库状态读取，区分普通分支、detached HEAD、尚无提交的仓库和未完成的 Git 操作。
- 按实际需要识别 merge、rebase、cherry-pick、revert 等会话；未支持的会话说明原因并引导在外部完成，不自动接管。
- 扩展现有 `merging` 协调方式，防止同一仓库同时进行互相冲突的写操作；界面禁用与主进程校验一致。
- 用户切换项目后，不把旧仓库请求结果显示到新项目；执行成功或失败后重新读取真实状态。
- 将实际进行中的 Git 写操作接入应用内更新的重启检查，避免更新中断操作。

验收：重复点击不会执行两次写操作；外部 Git 操作后刷新能反映真实状态；已有 MR 预检、提交和冲突恢复不回归。

本阶段只建设后续功能需要的基础，不提前引入通用任务队列、多仓库调度框架或全局命令系统。

### P1：工作区改动与 diff

范围：

- 按未暂存、已暂存和未跟踪分组展示文件，支持新增、修改、删除及重命名状态。
- 同一文件同时有已暂存和未暂存内容时，在两个分组分别展示正确差异。
- 查看文本统一 diff，显示文件路径、增删行及无改动状态。
- 未跟踪文本文件可预览；二进制文件明确提示不提供文本 diff。
- 大文件或大 diff 提供明确的展示限制，不因输出过大导致窗口卡死；阈值在实现时根据现有缓冲和界面性能确定。
- 正确处理中文、空格和特殊字符文件名；子模块显示状态，首期不进入其内部操作。

验收：文件状态与 Git 命令一致；查看已暂存差异不会混入未暂存改动；只读浏览不修改工作区、暂存区或分支；空列表和读取失败有明确反馈。

暂不实现：逐行或逐块暂存、内置代码编辑器、图片差异对比。

### P2：暂存、取消暂存与提交

范围：

- 支持单文件、所选文件及全部文件的暂存与取消暂存。
- 取消暂存只改变暂存区，保留工作区改动；兼容尚无首次提交的仓库。
- 提交面板支持标题和正文，明确提交的是暂存区内容；没有暂存内容时禁止普通提交。
- 检查必要的 Git 提交身份，缺失时说明配置方式，不静默修改全局配置。
- 沿用仓库 hooks 和签名配置；提交失败保留输入并显示实际原因，不自动跳过 hooks 或关闭签名。
- 成功后刷新文件状态、当前提交和分支信息；同名台账的状态遵循现有“标记有新修改”机制，不把新提交误报为 MR 已合并。

验收：提交仅包含已暂存内容；文件删除和重命名可正常提交；hooks 失败不会显示成功或清空提交信息；重复点击只产生一次提交。

暂不实现：Amend、空提交、提交签名配置界面、丢弃工作区修改。

### P3：创建与切换分支

范围：

- 从当前 HEAD、本地分支或明确的远程引用创建本地分支，并可选择立即切换。
- 校验分支名及重名、引用前缀冲突；复用现有分支选择信息。
- 切换已有本地分支；从仅存在于远程的分支建立跟踪分支，明确远程来源。
- 首期在工作区或暂存区不干净时阻止切换，保留改动并说明先提交或后续使用 Stash；不自动暂存或丢弃。
- 显示当前分支及上游；分支切换后刷新工作区，不自动修改项目 MR 目标或删除台账记录。

验收：中文和带斜杠的合法名称可用；同名远程分支能区分来源；切换失败不丢改动；当前分支显示与 Git 一致。

暂不实现：删除真实分支、批量分支清理、远程分支删除和分支重命名。

### P4：远程同步与 MR 衔接

范围：

- 将现有 Fetch 能力放入工作区，明确其只更新远程引用；多远程分别展示成功与失败。
- 显示当前分支的上游和 ahead / behind，并标明这些信息基于最近获取的远程引用。
- 提供“拉取到当前分支”，首期仅允许工作区干净时执行快进更新；分叉时停止，不自动 merge 或 rebase。
- 提供当前分支的普通推送。首次推送时明确远程和同名目标分支，并建立上游；已有上游按其来源显示目标。
- 推送遭拒绝时说明远端已有新提交，不自动强制推送。
- 推送成功后提供“提交 MR”入口，复用现有目标选择、预检和 MR 创建；推送失败不继续创建 MR。
- 沿用现有 Git 认证与网络超时处理，不将平台访问令牌当作 Git 认证配置。

验收：Fetch 不改变当前工作区；快进拉取正确更新当前分支；分叉或认证错误可理解；多远程不会推错目标；创建 MR 的源、目标与用户选择一致。

首期完成标准：在演示仓库中走通创建分支、修改文件、查看 diff、暂存、提交、推送、创建 MR、同步平台状态，并验证原来的批量 MR 与冲突流程仍可使用。

### P5：提交历史与 Stash

P5.1 提交历史：分页读取提交列表，显示哈希、作者、时间和说明；查看提交涉及的文件及 diff，支持复制哈希。先做线性列表，不实现复杂提交关系图。合并提交的展示方式必须明确，避免把不同父提交的差异混为一份。

P5.2 Stash：列出记录与说明，查看内容，支持保存、Apply、Pop 和删除。保存时明确是否包含未跟踪文件，默认不包含，始终不包含忽略文件；删除需确认。恢复冲突时保留现场并显示未解决状态，不能假设 Pop 已删除原记录；重新读取实际 Stash 列表。

验收：历史分页不重复或遗漏固定历史中的提交；大历史不一次性加载；Stash 保存和恢复覆盖已暂存、未暂存及可选未跟踪文件；恢复冲突不丢内容。P3 的切换提示可以引导打开 Stash 面板，但仍不自动 Stash。

### P6：Revert 与 Cherry-pick

范围：

- 从提交历史选择一个普通提交，预览操作目标及影响，再执行 Revert 或 Cherry-pick。
- Revert 产生新的反向提交，不移动历史；Cherry-pick 将所选提交应用到当前分支。
- 基于实际 Git 操作类型提供冲突处理、继续和取消，明确当前分支、原提交和当前进度。
- 复用已有冲突展示中适用的部分；不能直接复用 MR 专用的分支删除或收尾逻辑。
- 未完成会话重启后可识别，并提供继续入口。

验收：无冲突及有冲突路径均可完成；取消返回操作前状态；MR 冲突会话不被覆盖；失败不产生“成功”台账记录。

暂不实现：合并提交的 mainline 选择、批量提交编排及交互式编辑提交。

### P7：Rebase、Reset 与强制推送

本阶段不属于首期交付。实施前先形成具体交互方案，确认操作范围及用户可恢复的方式，再开发对应功能。

| 子阶段 | 计划范围 | 验收重点 |
| --- | --- | --- |
| P7.1 Rebase | 先支持普通 Rebase，提供继续、跳过、取消和恢复入口；交互式 Rebase 另行评估 | 冲突状态清晰，取消后回到原状态，不与 MR 会话混用 |
| P7.2 Reset | 分开说明 soft、mixed、hard 对历史、暂存区和工作区的影响；hard 要单独确认 | 预览目标提交和受影响内容；不能宣称 reflog 能恢复所有未提交内容 |
| P7.3 强制推送 | 仅考虑带明确预期远端提交的 force-with-lease，显示远程、分支及将被改写的历史 | 他人更新后拒绝覆盖；失败不得退回普通 force |

执行前保留必要的原提交信息并提供恢复指引；忽略文件、未跟踪内容及未提交修改不能仅依赖提交引用恢复。先评估具体操作的实际风险，不为尚未出现的理论边界堆叠额外机制。

## 5. 实现约定

- Git 命令只在 Electron 主进程执行，沿用 `execFile` 参数数组，不通过字符串拼接 shell 命令。
- 外部输入在 IPC / Git 输出进入系统的边界做必要校验，内部用准确类型流转，不层层重复校验。
- 仓库路径、文件路径、远程和引用应限定在对应操作允许的范围；文件参数使用正确的选项分隔或路径参数形式，避免特殊名称被当作命令选项。
- 优先复用现有 Git 方法、错误说明、组件和样式。只有实际复用或明显改善可读性时才拆分文件，不提前建通用 Git 框架。
- 如需台账结构变化，提供旧备份兼容与迁移；工作区文件内容和 Git 凭据不写入台账备份。
- 保留 hooks、Git 配置和系统认证行为，不自动覆盖全局配置，不展示或记录敏感凭据。
- 并发处理只覆盖实际存在的重复点击、异步返回和同仓库写操作冲突。其他低概率场景按项目规则先说明并确认，不擅自增加复杂逻辑。
- 复杂操作的确认是产品界面的一部分；执行计划本身不授权对用户真实仓库运行这些操作。

## 6. 每阶段验证与交付

| 验证层级 | 要求 |
| --- | --- |
| 静态检查 | 查看本阶段 diff，运行项目类型检查与构建，避免无关改动或依赖升级 |
| Git 自动化测试 | 在临时仓库、必要的本地裸远程中验证实际命令结果，核对 HEAD、引用、工作区和暂存区 |
| Electron 集成 | 验证 IPC、真实界面状态、禁用状态、错误提示和用户操作路径 |
| 既有流程回归 | 按影响范围检查单条 / 批量 MR、冲突预检、解决、放弃及备份兼容 |
| 平台检查 | Windows 与 macOS 分开记录；特殊文件名、编辑器打开和文件系统行为按平台验证 |
| 远程集成 | 仅在用户指定并授权的演示仓库验证真实认证、推送和 MR；本地裸远程测试不等同于平台集成通过 |

测试只覆盖有实际意义的行为和风险，不为简单界面代码编写镜像实现的测试。运行现有 UI 脚本前先检查其夹具和数据目录，避免改动用户日常台账。

每阶段完成后记录：实现文件、行为变化、已通过检查、未验证项及原因、已知限制。不得用“构建成功”替代 Git 操作或双平台验收。未经用户明确要求，不执行提交、推送、创建分支或远程发布；只生成中文 Conventional Commits 提交描述。
